# AI-Assisted Personal Investment App — Step 4
## Slice 1 — Evidence Layer Specification

**Version:** 1.0  
**Status:** Frozen for implementation  
**Purpose:** Build a stable, compact, provider-neutral Evidence Layer without breaking the existing OpenBB/yfinance flow.

---

## 1. Step 4 Objective

Slice 1 answers only:

> **What do we know about this company at this point in time?**

It does **not** answer:

- What should the investor think?
- Which research thread should become important?
- Is the stock attractive?
- What is the user's thesis?

Those belong to the AI Slice / Thread layer.

The Slice 1 flow is:

```text
Ticker
  ↓
OpenBB / yfinance
  ↓
Raw Evidence
  ↓
Normalized Research Snapshot
  ↓
EvidenceSnapshot database record
  ↓
AI Slice consumes normalized snapshot later
```

## 3. Evidence vs Interpretation Boundary

This boundary is frozen:

| Layer | Responsible for |
|---|---|
| OpenBB / yfinance | External data retrieval |
| OpenBBAdapter | normalization and data-quality handling |
| EvidenceSnapshot | persistence of raw + normalized evidence |
| AI Slice | interpretation and synthesis |
| ResearchThread | longitudinal research continuity |

The normalized snapshot must contain facts and derived calculations only.

It must NOT contain:

- buy/sell conclusions
- target prices generated by our app
- moat judgments
- thesis statements
- AI confidence about investment value
- thread importance
- narrative interpretation

---

## 5. Data Freshness

The Evidence Snapshot has two time concepts:

### Retrieval time

Stored in the existing database column:

```text
retrieved_at
```

### Source observation dates

Preserved inside:

- financial periods
- news dates
- analyst consensus date
- any provider-specific dates that survive normalization

Therefore the application should never assume that every section represents the exact same moment.

---

## 6. Section Failure Policy

Not every OpenBB section is equally critical.

### Required

`profile`

If profile retrieval fails:

```text
snapshot = failed
```

### Optional

The following sections may fail independently:

```text
quote
metrics
consensus
income
cash
news
```

If one fails:

```text
snapshot = success
+
warning
+
section marked missing
```

The application must never fabricate a missing value.

Example:

```json
"data_quality": {
  "sections_available": [
    "profile",
    "quote",
    "metrics",
    "news"
  ],
  "sections_missing": [
    "cash"
  ]
}
```

---

## 7. Data Quality Contract

`data_quality` must contain at least:

```text
snapshot_version
retrieved_at
provider
sections_available
sections_missing
warnings_count
```

The raw provider response remains stored in `raw_payload`.

This creates a clear audit chain:

```text
Provider response
      ↓
raw_payload
      ↓
normalization
      ↓
normalized_payload
      ↓
AI interpretation later
```

---

## 8. Operation Compatibility

The database operation remains:

```text
equity.profile
```

This is intentional.

Although the snapshot now contains multiple evidence sections, changing the existing operation string could break current Slice 1 code or historical queries.

The richer snapshot is identified through:

```text
normalized_payload.schema_version
```

and:

```text
request_params.snapshot_version
```

---

## 9. Request Parameters

The existing `request_params` JSON is extended, not replaced.

Example:

```json
{
  "symbol": "WMT",
  "provider": "yfinance",
  "snapshot_version": "research-snapshot-v2.1",
  "chart": false,
  "sections": [
    "profile",
    "quote",
    "metrics",
    "consensus",
    "income",
    "cash",
    "news"
  ]
}
```

`chart = false` is now explicit because the MVP does not generate K-line charts.

---

## 10. Record Count

The existing `record_count` database field remains.

For the multi-section snapshot it represents the total number of normalized raw records retrieved across the sections.

It is metadata only and must not be interpreted as the number of companies, stocks, or financial observations.

---

## 11. Content Hash

The existing `content_hash` continues to be calculated from the raw provider payload.

This allows the application to detect whether the provider response changed even when two requests concern the same ticker.

The hash is therefore based on:

```text
raw payload
```

not:

```text
AI output
```

## 13. Token-Efficiency Rules

Because the AI Slice will consume the normalized snapshot, Slice 1 should avoid unnecessary token growth.

Therefore:

1. Raw provider data remains in the database but is **not** automatically sent to Gemini.
2. `long_description` is bounded in normalized form.
3. News excerpts are bounded.
4. Maximum normalized news items = 8.
5. Cash-flow history = maximum 4 annual observations.
6. Latest income statement = one compact observation.
7. Provider-specific metadata is kept in `raw_payload`, not in the AI-facing normalized snapshot unless needed.
8. No chart data is collected for the MVP.

This preserves the information richness of the previous demo without turning the Evidence Snapshot into a raw-data dump.

## 14. Existing Code Mapping

### `models.py`

**No physical schema change.**

This is intentional to avoid migration risk.

### `adapters/openbb_adapter.py`

Responsibilities:

```text
OpenBB call
→ result conversion
→ normalization
→ compacting
→ section-level warnings
→ data-quality metadata
```

The adapter must remain independent of:

- FastAPI
- SQLAlchemy
- AI
- Research Threads

### `routes.py`

Responsibilities:

```text
request validation
→ Company lookup/create
→ Source lookup/create
→ EvidenceSnapshot pending row
→ adapter.get_equity_research_snapshot()
→ persist raw + normalized payload
→ return EvidenceSyncResponse
```

No AI logic is added to `/evidence/sync`.

## 16. What Step 4 Does NOT Do

Step 4 does not:

- assign Persistent Threads
- determine Thread importance
- write an investment thesis
- generate an AI report
- score the company
- calculate target price
- generate buy/sell conclusions
- create a knowledge graph
- create embeddings
- classify news sentiment

Those belong to later layers.

---

## 17. Step 4 Acceptance Criteria

Slice 1 is accepted when:

### A. Compatibility

Existing endpoints still work.

### B. Evidence completeness

For a normal yfinance/OpenBB company, the snapshot can contain:

```text
company
market
valuation
financial_health
analyst_consensus
recent_news
data_quality
```

### C. Graceful degradation

A missing optional provider section does not destroy the entire snapshot.

### D. Auditability

Every successful snapshot has:

```text
raw_payload
normalized_payload
content_hash
retrieved_at
```

### E. No AI contamination

No AI-generated interpretation is stored in the Evidence Layer.

### F. No chart dependency

The slice works without any K-line generation.

### G. Token discipline

Normalized evidence is compact enough to be passed to an AI report-generation step without sending the raw provider payload.

---

## 18. Frozen Step 4 Decision

The Evidence Layer is now defined as:

> **A compact, auditable, provider-neutral snapshot of current company evidence, with optional section failures and no AI interpretation.**

Its job is not to be the research report.

Its job is to give the AI Slice a reliable factual foundation.
